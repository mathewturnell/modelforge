Connect Modal

Modal is optional. A project action can use it only after you configure a private owner binding and deploy that project's fixed entrypoint. Starting a run never stages datasets, downloads models, creates an environment, or changes a budget.

1. Install and authenticate

python3.12 -m venv .venv
.venv/bin/python -m pip install 'modelforge-workbench[modal]==0.1.0a1'
.venv/bin/python -m modal setup

Let the Modal SDK store credentials in its own configuration. Never put tokens in a project manifest, source file, agent conversation, or Git repository.

2. Review, stage, and deploy the project

.venv/bin/python -m modal environment create <ENV>
# Follow the selected example's README to stage only its declared assets.
# Deploy its fixed project-owned Modal entrypoint to <ENV>.
.venv/bin/modelforge modal status --environment <ENV>

Review upstream access terms, exact revisions and digests, declared resources, timeouts, and the project's cleanup command before staging or deploying. The status command checks only local SDK and credential configuration; it does not verify an app or its assets.

3. Register the owner binding

.venv/bin/modelforge modal register --state-root <STATE> \
  --config <MODAL-BINDING.json>

Use the binding template in the selected example's README. The binding is kept in owner-only local state and identifies the exact environment, app, function, planned resources, deployment digest, and provider-side assets. Project source and browser requests cannot replace those values.

4. Confirm and start in the workbench

Select the Modal target and review its binding digest, environment, and planned resources. The run button remains disabled until you explicitly confirm the billable action. Planned resources are not a quote or budget cap, and actual provider charges can differ.

Equivalent action run --executor modal CLI launches require an idempotency key, the current binding digest, and the explicit --confirm-billable flag. ModelForge does not enforce a budget or promise free execution.

If a launch response is interrupted, leave the target and input unchanged and retry: this tab reuses the same launch identity. Do not make a second request just because live status is unavailable.

5. Recover, inspect, and clean up

.venv/bin/python -m modal app list --env <ENV>
.venv/bin/python -m modal app logs <APP> --env <ENV>
.venv/bin/python -m modal app stop <APP> --env <ENV>
.venv/bin/python -m modal billing report

Use Recover provider status on an unavailable retained run to reattach to its recorded provider call; recovery never starts a new call. Stopping an app can interrupt calls. Check the exact app and environment first. Removing local state does not stop remote work.

Troubleshooting

  • If the SDK is missing, reinstall the modal extra in the same environment as ModelForge.
  • If credentials are unavailable, rerun .venv/bin/python -m modal setup and inspect the active profile. Do not copy token values into ModelForge.
  • If an app or environment is missing, verify the explicit --env <ENV> value and deploy the packaged app there.
  • If a call was accepted but the client stopped, recover the recorded run from the workbench rather than starting a second run.
  • If local state and Modal disagree, inspect app logs and billing in Modal before stopping the exact app.
