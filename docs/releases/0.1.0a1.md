# ModelForge 0.1.0a1 — public source alpha

- Published: 2026-09-11
- Support matrix: Linux x86-64, CPython 3.12
- License: Apache-2.0, with recorded upstream terms retained where applicable
- Distribution: source repository only; no package registry or hosted service

## Why this release exists

This alpha establishes a small, inspectable local workbench around project-owned
ML code. It is intended for developers who want coding agents and humans to use
the same visible workflow without making the agent, browser, or project process
the owner of run history or scientific evidence.

The release proves a deliberately narrow path: inspect a declared project,
select a bounded input, create a durable run before execution, invoke an
owner-configured local or optional Modal action, validate the typed result, and
recover digest-checked artifacts in the loopback workbench.

## Highlights

- Browser-neutral project manifest and authored-capability inspection that does
  not import project code or imply execution authority.
- One Project → Dataset → Run → Executor → Artifact application path shared by
  the CLI and token-protected loopback browser.
- Durable project-scoped SQLite run state created before process or provider
  submission, with explicit requested, running, cancellation, and terminal
  states.
- Bounded local subprocess execution, process-group cancellation, truthful
  failure reconciliation, and completed-run recovery after browser or service
  restart.
- Action-specific inference and prompt-result validation with size- and
  SHA-256-checked artifacts, safe browser projections, and range-capable video
  serving.
- An approved compiled React workbench for project switching, dataset and
  prompt configuration, run status, bounded process logs, operational progress,
  checked native results, cancellation, and durable recovery.
- A capability-derived local product shell that keeps planned product areas
  visible while disabling controls that lack a real server-owned service.
- A dependency-free Synthetic Threshold Lab for installation and lifecycle
  smoke testing.
- Rights-reviewed integration code and explicit setup declarations for BDD100K,
  Qwen2.5-7B, SoccerNet Tracking, and TasteMatch. External source, datasets,
  weights, checkpoints, caches, and outputs remain user-acquired and outside
  the repository.
- Optional fixed Modal action bindings with explicit account setup and billable
  confirmation. Provider execution is not part of ordinary installation or CI.

## Start here

```bash
git clone https://github.com/mathewturnell/modelforge.git
cd modelforge
python3.12 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/modelforge demo run --state-root /tmp/modelforge-alpha-state
.venv/bin/modelforge serve --state-root /tmp/modelforge-alpha-state
```

The demo is synthetic, offline, and inference-shaped. It validates operational
behavior; it is not evidence of model quality.

For real projects, begin with a read-only plan:

```bash
.venv/bin/modelforge examples setup plan \
  --example bdd100k-road-scene-lab \
  --external-root /srv/modelforge-examples
```

See [example setup](../example-setup.md) before acquiring external material and
[the Modal tutorial](../modal.md) before enabling a remote target.

## Security and trust boundary

ModelForge is local-first, not a sandbox. Registered project actions are trusted
code and run with the invoking user’s permissions. The browser server is
loopback-only and bearer-token protected; owner state uses restrictive paths and
file modes; public artifact projections omit storage locations and revalidate
registered bytes before serving them.

Keep credentials, `.env` files, private repositories, datasets, model weights,
checkpoints, and run outputs outside the ModelForge source tree. Read
[SECURITY.md](../../SECURITY.md) for the supported boundary and reporting path.

## Known limitations

- Frozen evaluation and promotion, polygon/line/point annotation, write-capable
  Git and assistant actions, general repository import, and deployment remain
  visible product areas without public service implementations. Registered
  local training, box annotation, conversation curation, telemetry charts, and
  read-only project assistant chat are implemented.
- Dynamic project-supplied UI code and arbitrary unreviewed action interfaces
  are not included.
- Active local processes do not resume after abrupt host loss. A disappeared
  unfinished process becomes an explicit failure; completed records recover.
- HTTP and owner runtime-configuration formats are experimental alpha surfaces.
- Real-project integrations require separately acquired upstream dependencies
  and assets. Their evidence is bounded to recorded inputs and environments and
  is not a model-quality claim.
- Modal support is an optional alpha integration, not a general provider,
  availability, price, or budget guarantee.
- Native 200% browser zoom and an end-user screen-reader session remain
  unverified alpha checks. Automated keyboard, narrow-layout, axe, and browser
  accessibility-tree checks do not replace those human sessions.

## Verification and provenance

The `public-alpha` GitHub Actions workflow gates Python tests and static checks,
source and wheel builds, archive inspection, installed-package smoke testing,
compiled browser journeys, repository/history exposure scanning, and an
independent Gitleaks history scan. The required aggregate release gate passes
only when every job succeeds.

The source repository uses a reviewed single-root history and a complete
`public-source-manifest.json`. Nineteen retained real-example Python files have
individual provenance dispositions: seventeen use Apache-2.0 and two
MeMOTR-derived BDD100K files preserve their recorded upstream terms alongside
the Apache-2.0 ModelForge additions. The 101-file restored React source, asset,
configuration, and lock inventory records the approved clean recovery, exact
archive references, and bounded public adaptations.
